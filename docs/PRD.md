# OwlDesk — 需求文档（PRD）

> **Sleepless Desk for Tokenized US Stocks** · 24 小时美股研究台
> Bitget AI Hackathon Season 2 · 赛道 3：AI Trading Desk（投研看板）
> 版本 v0.1 · 2026-09-08 · 提交截止 2026-09-21

---

## 1. 一句话定义

OwlDesk 是一个自然语言驱动的 24 小时美股研究台：**夜里替你盯盘并生成简报（信息提炼），白天替你起草订单计划、你签字后才执行（执行辅助）**。AI 处理信息，交易员做最终决策——这正是赛道 3 的定义。

- 猫头鹰（Owl）= 夜间值守；Desk = 交易台。
- Slogan：*"The desk that never sleeps."*

## 2. 背景与切入点

- 代币化美股（Bitget rToken）已实现 7×24 交易，但用户要睡觉：**美股交易时段 ≈ 亚洲用户的睡眠时段**，这段时间发生的行情、新闻、财报，醒来时已错过最佳反应窗口。
- 现有工具两极分化：要么全自动交易（不放心），要么纯看板（不省心）。OwlDesk 取中间态——**AI 全程值守、起草一切，但签字权永远在人**。

## 3. 产品结构：两个核心模块 + 一个对话入口

```
┌─────────────────────────────────────────────────────┐
│                    OwlDesk Chat                      │
│         （自然语言入口，所有能力的对话式调用）           │
├──────────────────────────┬──────────────────────────┤
│  模块 A · Overnight Brief │  模块 C · Order Draft Desk │
│  夜间简报（信息提炼）        │  拟单助手（执行辅助）        │
│                          │                          │
│  · 夜间盯盘自动巡检         │  · NL → 结构化订单计划       │
│  · 醒来即读的晨报           │  · 风控校验 + 风险标注        │
│  · 追问式解读（带数据引用）   │  · 人工签字 → paper 下单     │
│  · 事件时间线（财报/新闻）    │  · 挂单状态跟踪              │
└──────────────────────────┴──────────────────────────┘
              底座：Bitget Agent Hub（market / signal / trade）
```

## 4. 功能需求

### 模块 A：Overnight Brief（夜间简报）→ 冲"信息提炼"子主题

**目标**：用户睡醒后 1 分钟内了解"夜里美股发生了什么、为什么、今天该看什么"。

| 编号 | 需求 | 说明 | 优先级 |
|---|---|---|---|
| A1 | Watchlist 管理 | 添加/移除关注的 rToken 美股（默认预置 NVDA/TSLA/AAPL 等热门标的） | P0 |
| A2 | 夜间自动巡检 | 交易时段内定时（如每 15–30 分钟）拉取价格变动、新闻、情绪，按阈值触发记录（异动、新闻、财报事件） | P0 |
| A3 | 晨报生成 | 时段结束后（或用户唤醒时）汇总整夜事件，LLM 生成结构化晨报：**隔夜行情总览 / 逐标的三段式解读（发生了什么·为什么·怎么看）/ 今日关注点** | P0 |
| A4 | 追问解读 | 对晨报任意条目或自由提问（"NVDA 盘后为什么跌？"），Agent 组合行情+新闻+情绪生成带引用的回答 | P0 |
| A5 | 事件时间线 | 每标的的夜间事件流水（价格异动点、新闻发布点、财报节点）可视化 | P1 |
| A6 | 晨报订阅 | 邮件/推送晨报摘要（演示可用邮件） | P2 |

**验收标准（P0）**：预设 5 个标的跑一整夜，次日能打开页面看到完整晨报；对任一标的一句追问能拿到含数据依据的回答。

### 模块 C：Order Draft Desk（拟单助手）→ 冲"执行辅助"子主题

**目标**：把"想下单"到"实际下单"之间的事务性劳动交给 AI，但决策权留给用户。

| 编号 | 需求 | 说明 | 优先级 |
|---|---|---|---|
| C1 | NL 起草订单 | 自然语言输入（"TSLA 跌破 220 挂半仓止损"），Agent 生成**结构化订单计划卡**：标的、方向、类型（市价/限价/条件单）、数量、触发条件、有效期 | P0 |
| C2 | 风险标注 | 每张计划卡自动附风险检查：仓位占比、与当前持仓的对冲/叠加关系、偏离现价幅度、异常输入提醒（数量过大、方向与持仓矛盾） | P0 |
| C3 | 人工签字确认 | 明确的两步流程：Draft（AI 拟单）→ Sign（人点确认）。无签字不下单；签字记录留痕 | P0 |
| C4 | 模拟盘执行 | 确认后经 paper trading（Demo API Key）提交 `strategy_order`，返回订单状态 | P0 |
| C5 | 挂单跟踪 | 列表展示已签署订单的状态（待触发/已成交/已取消），支持一键撤销 | P1 |
| C6 | 情景快速拟单 | 结合模块 A 的晨报：在简报条目上直接"就此起草订单"（如"看新闻说 X 要反弹，帮我拟个试仓单"） | P1 |

**验收标准（P0）**：三句自然语言指令能分别生成正确的市价单/限价单/条件单计划卡；拒绝确认则绝不产生任何订单；确认后在模拟盘查到订单。

### 对话入口（Chat）

| 编号 | 需求 | 优先级 |
|---|---|---|
| H1 | 单一聊天框统一调用所有能力：查行情、问简报、拟订单、查挂单 | P0 |
| H2 | 回答带数据来源标注（行情时间戳 / 新闻链接），不编造 | P0 |

### 明确不做（Hackathon 边界）

- 不做真实资金下单（全部 paper trading）
- 不做策略自动循环执行 / 全自动 Agent（那是赛道 2，且偏离"人签字"定位）
- 不做复杂回测引擎（Playbook 已有，必要时链接跳转即可）

## 5. Agent Hub 如何赋能（提交表单 Q7 素材）

| 能力 | 用的 Agent Hub 组件 | 用法 |
|---|---|---|
| 行情数据 | `market` 模块（公开数据，免 Key） | rToken 美股实时/历史价格、异动检测 |
| 宏观解读 | `bitget-signal` · `macro-analyst` | 晨报"为什么"的市场背景部分 |
| 新闻简报 | `bitget-signal` · `news-briefing` | 夜间新闻事件流水、晨报素材 |
| 市场情绪 | `bitget-signal` · `sentiment-analyst` | 情绪标注进简报与计划卡 |
| 技术面 | `bitget-signal` · `technical-analysis` | 追问解读、计划卡的技术位参考 |
| 持仓/账户 | `account` 模块 + **`--read-only`** | 只读拉取持仓做仓位风险标注 |
| 订单起草与执行 | `trade` 模块 · `strategy_order` + **`--paper-trading`** | 签字后提交条件单/策略单（Demo Key） |
| 元能力 | `discover` / `raw` | 89 个 UTA v3 操作按需调用 |

**赋能叙述（一句话版）**：OwlDesk 不是重新造数据管道，而是把 Bitget 官方 Agent Hub 当作"交易台的桌子"——行情、新闻、情绪、持仓、下单五个面全部长在 Agent Hub 的 89 个 UTA v3 操作上；分析侧全程 `--read-only`，执行侧 `--paper-trading` + 人工签字，权限最小化。

**Playbook 的角色（可选加分项）**：简报的"今日关注点"可附一条 Playbook 链接/一句话策略，作为"从看板到策略"的延伸演示。

## 6. 技术架构

```
Next.js (App Router) 全栈
├── 前端：Chat 界面 + 晨报卡片 + 订单计划卡/签字面板 + 时间线
├── 后端 API Routes：
│   ├── /api/chat        —— LLM 编排（function calling 调 Agent Hub 工具）
│   ├── /api/brief       —— 晨报生成与查询
│   ├── /api/cron        —— 夜间巡检调度（Vercel Cron / node-cron）
│   └── /api/orders      —— 计划卡 CRUD、签字、paper 下单
├── Agent Hub 接入层：
│   ├── @bitget-ai/bitget-agent-sdk（直接嵌 SDK，89 操作）
│   │     · 分析调用：--read-only 语义（只挂 market/account 只读工具）
│   │     · 执行调用：Demo Key + --paper-trading
│   └── bitget-signal 五技能（免 Key，分析引擎）
├── LLM：Qwen API（用 30U 赞助额度）/ 可切换 Claude
└── 存储：SQLite/JSON 文件（演示级；watchlist、晨报、订单留痕）
```

**安全原则**：API Key 只存环境变量；下单路径必须经过"计划卡 → 人确认"两步；演示账号仅用 Demo Key。

## 9. 风险与开放问题

1. **rToken 标的覆盖**：Agent Hub market 模块里代币化美股的可查代码清单需第一周实测确认；若覆盖不全，fallback 用公开美股行情做展示 + rToken 做执行演示。
2. **signal 技能的实际输出质量**：五技能是预置 prompt 的 MCP 能力，返回深度未知，需要实测后决定晨报里各占多少权重。
3. **夜间调度的托管**：Vercel Cron 免费档粒度与演示时区问题；最差方案本地常驻进程 + 录屏演示。
4. **Paper trading 的 Demo Key**：注册与申请流程当天验证，阻塞则用真实只读 Key + 模拟撮合（本地记账）兜底。
5. **子主题二选一**：两模块都完成后看完成度，哪边演示更顺就报哪边（表单提交时才需要定）。
